Security

What it checks, and what it can't.

keydrop protects the way into the keychain. It does not protect the keychain from software already running as you. The reasoning behind each check is in the docstring at the top of the script; the invariants every implementation keeps are in section 4 of the spec.

01 · How it works

One path for the value, checked on every request.

Four parties on your machine and one browser. The teal line is the only route the value ever takes.

the value everything else any channel you like
  1. Request. Your tool runs keydrop request <name>. keydrop checks the name, binds a listener on 127.0.0.1, asks tailscale serve for an HTTPS route to it on the same port number, confirms the route exists, and only then accepts connections.
  2. Link. It prints the link once and detaches. The path carries a 256-bit token from a cryptographically secure generator.
  3. Deliver. The link reaches you over whatever channel the tool already has. A chat message is fine: to anyone the tailnet won't authenticate as you, the link is useless.
  4. Submit. You open it on a device signed in to your tailnet and submit the value. Every request is checked in this order: the route is still keydrop's own, the Host is on the allowlist, Tailscale-User-Login is the owner, the token matches in constant time. Anything else gets a bare 404.
  5. Store and verify. keydrop hands the value to security -i on stdin as hex, reads it back, and compares digests. Only a match counts as stored.
  6. Close. The page says "Stored. You can close this." keydrop closes the route, confirms with Tailscale that it's gone, and exits.
  7. Read back. Your tool runs keydrop get <name> and passes the value on without printing it.

A request also ends on the TTL, after five bad requests, on keydrop cancel, and on any signal or crash. Every one of those paths closes the route. Routes left by a killed process are found and removed later, and only routes keydrop itself created are ever removed.

02 · Threat model

What it defends against, and what it doesn't.

Defends against

  • The value reaching a chat, a log or argv. It goes from the browser to keydrop, then to security -i on stdin as hex. Logs hold only name, time and outcome. Every write is read back before the page says Stored.
  • Other people on your tailnet. Every request needs the owner's Tailscale-User-Login, which tailscale serve sets from the connection and peers can't forge. Lookalike spellings of that header are refused.
  • Guessing the link. The token is 256 bits, compared in constant time. On a one-shot or vault link, five bad requests end it early. On the home page only a wrong token sent with your login counts, and five in 24 hours lock it until keydrop home --unlock.
  • Browsers on this machine. An exact Host allowlist stops DNS rebinding. Form tokens and Fetch Metadata stop cross-site posts, and a cross-site request can't run up strikes on the home page.
  • A loopback port left open to the tailnet. Under userspace networking, tailscaled forwards tailnet traffic to 127.0.0.1 on the same port when serve doesn't claim it. keydrop uses the same port on both sides, listens only after the route exists, and checks on every request that the route is still its own, exiting if not.
  • Leftover routes. Teardown on every exit path and a reap for killed processes. keydrop keeps a ledger of every serve route it creates and only sweeps ledger entries no live record owns, and only while the route still points where keydrop pointed it. A route keydrop didn't create is never removed.
  • Funnel. If Funnel gets turned on for a page's port, the page treats its route as gone: it answers a bare 404 and exits.
  • Reading values through a page. The vault and home pages are write-only.

Doesn't defend against

  • Anything running as you on this machine. It can run keydrop get or security itself. keydrop protects the way into the keychain, not the keychain.
  • Local processes connecting to 127.0.0.1. They can send any header. They still need the token.
  • A compromised device signed in as you, or anyone holding the link. Treat a link like a short-lived password.
  • A compromised tailscaled, or a tailnet admin.
  • Untested setups. The port analysis was worked out against tailscaled with userspace networking. A kernel-TUN tailscaled, such as the macOS app, hasn't been analysed.
03 · Two more pages

A vault page and a home page. Both write-only.

Same token in the path, same owner check, same route check on every request, same teardown. Neither ever renders a stored value, so a screenshot, a browser cache or someone over your shoulder gets nothing.

keydrop vault

A session link, held open for one TTL. The page lists names, notes and times, and lets you add, replace and delete entries under the service prefix. Every post needs the session's form token as well as the path token. Delete asks first. The Done button ends the link.

keydrop home

The vault page with no TTL, meant to stay up under launchd. In place of the TTL it has a lockout that survives restarts, a write rate limit, an audit log and a stop switch. Only bad requests carrying your login and same-origin Fetch Metadata count as strikes, so a stranger or a cross-site page can't lock you out.

The kill switch

keydrop home --stop takes the route down and leaves a flag that keeps it down. It reports success only once serve status shows nothing on the home port still pointing at the page. Five bad requests in 24 hours lock it the same way. keydrop home --unlock brings it back; --new-link replaces the link without a restart.

Notes from the vault page are stored in plain text in the state dir, so don't put secrets in them.
